Rajshahi University Student Management System

2026Backend Laravel · PHP · MySQL · REST API
Live GitHub

A production student information system and central student-data service for Rajshahi University. One authoritative student record is served two ways: a server-rendered web application with organization-scoped panels for university officers, and a versioned REST API that gives other campus systems only the fields their token entitles them to. Live across the Academic Section, dean offices, departments, and residential halls.

Problem

Student data lived in separate spreadsheets across the Academic Section, dean offices, departments, and halls. Copies went stale between data dumps, a correction made in one office never reached the others, access to the database was all-or-nothing when it needed to be scoped, and nothing recorded who changed what.

Solution

A Laravel monolith holding one authoritative student record, with access scoped by organizational unit and by field at the query level. A correction made by an Academic Section officer is immediately visible to every downstream system — results, exam form fill-up, medical, hall automation — because those systems read the record over a permissioned API instead of keeping their own copy of it.

What the System Serves

These are live production figures, not a pilot. The system is the single authoritative record for every student the university has admitted, and the offices and campus systems below depend on it as part of their daily work rather than occasionally.

Key Features

  • Fast student lookup by identifier, with sectioned record views — basic, personal, contact, identity, academic
  • Record editing with cross-entity integrity validation and admission lifecycle handling (cancellation, reinstatement)
  • 50+ individual permissions, granted through a role or attached directly to a single user, gating view, edit, and export separately — down to individual sections of a student record
  • Five scoped panels — Super Admin, Academic, Dean, Department, and Hall — each confined to one faculty, department, or hall, with no visibility outside that scope
  • Official PDFs — admission forms, registration cards, migration certificates — with correct Bengali typesetting, embedded photographs, barcodes, and QR codes
  • Excel exports composed by the officer — chosen columns emitted in the order they were picked, with filters on department, hall, session, and home district, and permission-gated fields excluded
  • Admin dashboard with live counts by faculty, department, hall, and session, split by gender and totalled, plus hall occupancy and cohort statistics
  • Admission statistics summarising merit versus quota intake, broken down by individual quota type and filterable by faculty, department, hall, or session
  • Versioned integration API where each token carries its own permission set — the hall automation system's token reads basic student data and can write only resident status
  • Full database backup facility producing complete snapshots of the authoritative record on a regular schedule
  • Activity log carrying actor attribution and field-level diffs
  • Legacy student module giving pre-system students bilingual name fields and document access

Challenges & Engineering Deep Dive

Scoping Access by Organizational Unit and by Field

A hall clerk, a department officer, a dean, and an Academic Section officer all need the same student record but a different slice of it — and "different slice" varies per person, not just per job title. Filtering in the view layer would have been the easy path — and the wrong one, since the unauthorized rows would still be loaded and one missed template condition would leak them.


How I solved it: The system defines 50+ individual permissions, and access is enforced at the query level rather than the display level. Permissions can be granted through a role or attached directly to one user, so an officer's access is composed rather than picked from a fixed list of job titles. View, edit, and export are separate permissions, and the unit they apply to is a single section of the student record — an office can be allowed to read contact details without editing them, or to edit academic fields while never seeing identity ones.


Organizational scope is a second, independent axis: a user can be bound to one faculty, department, or hall, and their queries are constrained so students outside that scope are never returned at all. A single declarative configuration maps each section of the record to the capability required to read it and the rules used to validate it, so adding a field means editing one map rather than hunting through controllers and Blade templates. There is no self-registration anywhere in the system — accounts are provisioned by administrators only.

Official Documents with Correct Bengali Typesetting

Admission forms, registration cards, and migration certificates are official university documents — they have to render Bangla script correctly, carry the student's photograph, and be verifiable in hand. Complex-script shaping is where most PDF pipelines quietly produce broken output.


How I solved it: Documents are rendered from the live record at print time rather than stored as static files, so a correction shows up on the next printed copy instead of leaving a stale PDF in circulation. The generator handles complex-script shaping for Bangla, embeds photographs, and stamps barcodes and QR codes for verification. Registration cards ship in two layout options, and migration certificates are generated for outgoing students on demand.

Spreadsheet Exports Officers Build Themselves

Every office wanted a list, and no two wanted the same one — the Academic Section needed one set of columns in one order, a dean's office another, a hall provost another again. Shipping a fixed report per request would have meant a developer in the loop for every new question anyone thought to ask.


How I solved it: The export is composed by the officer, not hard-coded. They pick which columns to include, and the order they pick them in becomes the column order in the file, so a spreadsheet can be shaped to match whatever form or report it is feeding. Rows are narrowed with filters on department, hall, session, and home district, in any combination. The same permission rules that govern the screen govern the file — a column the officer cannot view is not offered in the picker and cannot appear in the output, so the export can never become a way around the access model.

Statistics the Administration Can Answer With

Administrative questions arrive with a deadline attached — how many students in this faculty, how many women in that hall, how much of this session's intake came through merit rather than quota, and which quota. Under the old arrangement each answer meant collecting spreadsheets from several offices and hoping none of them was stale.


How I solved it: Counts are a first-class feature rather than a report someone runs. The dashboard breaks the student body down by faculty, department, hall, and session, split by gender and totalled, and a statistics view narrows the same figures by any of those dimensions. Admission intake is summarised as merit against quota, with each quota category counted separately, so a question about intake composition is answered on screen instead of by hand.


The figures are computed live from the authoritative record, not from a nightly rollup, so they cannot be out of date — and because aggregation runs inside the database rather than in PHP, cohort scale does not slow the page down.

Integration API — Capabilities, Not Access

The system is not a destination application — it is the student-data service the rest of the campus runs on. The examination result system, exam form fill-up, the university medical system, and hall automation all read their student data from it, so it sits on the critical path of processes with hard deadlines: if it is slow during form fill-up week, four systems are slow. The obvious request from each of them was always the same, though — a database account, or a nightly dump. Both recreate the original problem: a second copy that drifts, and far broader access than the consuming system actually needs.


How I solved it: A versioned REST API issues tokens carrying an explicit capability checklist — the same permission vocabulary the web panels use, applied per token rather than per user. Responses include only the sections that token is entitled to, and writes are scoped just as tightly: the hall automation system's token reads a student's basic data and can write exactly one field, resident status, with identity documents and contact information never reaching it in either direction. Business logic for statistics, exports, updates, and documents lives in a service layer beneath both the web and API surfaces, so the two never drift apart, and cohort-scale operations run through validated transactional endpoints. Because several systems depend on this one, performance and scalability were design constraints from the start rather than later optimisations.

Performance and Scalability as a Shared Dependency

Officers work on older campus hardware over a university network, and four other campus systems query this one for their student data. With 53,000+ records behind it, full-university exports and document batches routine, and other services waiting on its responses, slow work here does not stay here — it propagates.


How I solved it: The application is server-rendered by design; an SPA would have added overhead to what are fundamentally form-and-table workflows. Lists return nothing until a search is actually performed, queries select only the columns being displayed, and dashboards aggregate inside the database rather than in PHP. Spreadsheet exports and document generation stream in chunks, so memory stays constant no matter how large the batch, and API responses are built from the same service layer so a consuming system never pays for work it did not ask for.

Auditability and Authorization as Source Code

For a record that many offices can edit, "who changed this, and when?" has to have an answer. Routing-table permission lists tend to answer it badly — the rule sits far from the action it protects, and the two drift apart as the system grows.


How I solved it: Capabilities are declared adjacent to the protected action rather than in a routing table, so the guard is visible in the same place as the code it guards. Model-level activity logging records every change with actor identity, timestamp, and field-level diffs, and the same attribution covers permission modifications, exports, and integration calls. Integration tokens are managed through explicit capability checklists rather than free-form scopes. Because the system is deliberately the only authoritative copy of the data, a full database backup facility takes complete scheduled snapshots — centralization removes the accidental redundancy of scattered spreadsheets, so the recovery path has to be explicit rather than assumed.

Why There's No Public Login

The system is not restricted to the campus network — studentdb.ru.ac.bd is live and reachable from anywhere. What is restricted is who can sign in. It holds protected, identifiable student records, so accounts are institution-provisioned: only authorised university offices, the maintenance team, and university employees hold credentials. Everything past the login screen is live student data, so there is no public login to hand out and nothing beyond that screen to show.
