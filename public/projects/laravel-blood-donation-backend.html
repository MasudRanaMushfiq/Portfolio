Laravel Blood Donation Backend

2026Backend Laravel · PHP · REST API
GitHub Live

A RESTful Laravel backend for blood donation management — donor CRUD, blood requests, emergency handling, and location-based filtering with a web admin dashboard.

Problem

Blood donation organizations lacked a centralized digital platform to manage donors, track blood requests, and handle emergency situations efficiently.

Solution

Created a RESTful API with Laravel that manages donor registrations, blood requests, emergency alerts, and location-based filtering, paired with an admin dashboard.

Key Features

  • Donor registration and profile management
  • Blood request creation and tracking
  • Emergency alert system
  • Location-based donor filtering
  • Admin dashboard for oversight

Challenges & Engineering Deep Dive

Multi-Module Architecture Coordination

The application is built with nine independent modules — User, Donar, General, Admin, SuperAdmin, Dashboard, Reminder, JelaAdmin, Chat — each with its own controllers, models, routes, and views. Managing cross-module dependencies (e.g., Donar needing data from General for location filtering) without circular references or code duplication was a significant architectural challenge.


How I solved it: Leveraged nwidart/laravel-modules with a clear dependency hierarchy: shared infrastructure (General) sits at the bottom, domain modules (Donar, User) depend on it, and administrative modules (Admin, SuperAdmin, JelaAdmin) consume domain modules. Each module registers its own service provider for auto-discovery. The ModuleServiceProvider base class provides common functionality like model helpers and response formatters, keeping the modules lean and focused.

OTP-Based Authentication Flow

Blood donation platforms serve a diverse user base — including non-tech-savvy donors who may not remember complex passwords. Traditional email/password auth creates friction. The app needed a phone-based OTP flow that is both secure and beginner-friendly.


How I solved it: Implemented a two-step authentication pipeline using Laravel Sanctum. The login endpoint accepts a phone number, generates and stores an OTP (hashed) in the users table, and sends it via SMS. The verifyOtp endpoint validates the submitted OTP against the stored hash, issues a Sanctum token on success, and cleans up the OTP. Tokens are scoped with abilities (donor, admin, etc.) so the same auth system works across all roles.

Location-Based Donor Search with Zila/Upazila Hierarchy

Finding a blood donor nearby is the core use case. Bangladesh's administrative hierarchy (Division → Zila → Upazila) needed to be modeled accurately in the database, with an API endpoint that could filter donors by location level and blood group instantly.


How I solved it: Created Zila and Upazila Eloquent models with a proper one-to-many relationship. The Donar model stores zila_id and upazila_id as foreign keys with eager-loadable relationships. The search endpoint accepts optional zila_id, upazila_id, and blood_group query parameters, building a dynamic query with when() conditionals that returns only active, eligible donors. Results are paginated and sorted by donation recency so the most available donors appear first.

Emergency Blood Request & Alert System

Emergency blood requests require immediate attention — a patient in critical condition cannot wait for manual donor matching. The system needed to prioritize emergency requests, notify potential donors, and track the urgency status through fulfillment.


How I solved it: The EmergencyRequest model includes a priority enum (critical/high/normal) and a status pipeline (pending → matched → fulfilled → cancelled). Emergency requests are fetched with a scopeEmergency() that orders by priority and creation date. Admin and JelaAdmin dashboards highlight emergency requests with a red badge. When a request matches available donors by location and blood group, the system creates donor notification records that display on the donor's next app session.

App Version Update System for Android

The mobile app (if any companion apps are built) needs a way to force or optionally update the APK when breaking API changes are deployed. Without version management, users on old builds would encounter cryptic errors or data inconsistencies.


How I solved it: Created an AppVersion model with fields for version_code (integer), version_name (string), is_force_update (boolean), and a file or url for the APK. The API exposes a /api/version/latest endpoint that returns the current version info. The app calls this on launch, compares the version code, and shows either a dismissible "Update Available" prompt or a mandatory "Update Required" screen. The admin panel has a dedicated AppVersionController for uploading new releases.

Role Hierarchy & Granular Permission Separation

The system has five user types — SuperAdmin, Admin, JelaAdmin, Donor, and Normal-User — each with radically different access levels. SuperAdmin manages everything, Admin handles regional operations, JelaAdmin works at district level, and Donor/User have personal profile access. Hard-coding this hierarchy would be brittle and insecure.


How I solved it: Implemented Spatie Laravel Permission with five well-defined roles and a cascading permission model. SuperAdmin inherits all permissions via SuperAdmin gate. Admin gets regional-level CRUD plus JelaAdmin management. JelaAdmin gets district-scoped read/write. Donor can manage their own profile and donation history. Middleware aliases in app.php guard every route group, and a custom EnsureUserHasRole middleware returns a consistent 403 JSON response for API calls — never exposing unauthorized functionality.
