Ticket Booking App

2026App React Native · TypeScript · Expo Go · Firebase
GitHub Live

A full-featured React Native mobile app built with Expo Go and Firebase. Delivers a seamless ticket purchasing experience with real-time backend integration and cross-platform support.

Problem

Event-goers needed a convenient mobile solution to browse, book, and manage tickets on the go. Existing platforms were clunky and lacked real-time updates.

Solution

Built a cross-platform React Native mobile app with Expo Go and Firebase backend, providing a seamless ticket browsing and purchasing experience with real-time synchronization.

Key Features

  • Cross-platform (iOS & Android) with Expo Go
  • Firebase real-time backend integration
  • Ticket browsing and purchase flow
  • Booking history and management
  • Push notifications for updates

Challenges & Engineering Deep Dive

Seat Locking & Concurrency Prevention

When multiple users browse the same bus simultaneously, two people could select the same seat — resulting in double-booking chaos. Traditional relational databases handle this with row-level locks, but Firestore's NoSQL model offers no such isolation guarantees.


How I solved it: Implemented a two-layer seat state: bookedSeats (permanently taken) and lockedSeats (temporarily frozen for 10 minutes). When a user starts selecting seats, the app writes to lockedSeats with a lockedAt timestamp using firebase.firestore.FieldValue.arrayUnion() for atomicity. A background interval periodically checks and releases expired locks (Date.now() - lockedAt > 600000). The seat grid component subtracts both bookedSeats and lockedSeats from the available pool, and the booking button is disabled if any seat is locked by another user.

Firestore Data Modeling Across Six Collections

The app spans six Firestore collections — admins, users, buses, bookings, complaints, notifications — each with complex sub-fields like busDetails.seats and booking.seatNumbers[]. A single booking action must atomically update the bus document's bookedSeats, create a booking document, and append to the user's bookingIds. Without transactions, partial failures would corrupt data.


How I solved it: Used Firestore runTransaction for critical booking write paths, ensuring all-or-nothing semantics. For non-critical operations like complaint submission, used batched writes via writeBatch. The bus document stores seat state as an array of strings (["1A", "1B"]) using arrayUnion / arrayRemove to avoid race conditions. User documents reference bookings via bookingIds arrays, enabling efficient lookup without requiring a full collection scan.

Payment Verification Without a Payment Gateway

Integrating a full payment gateway (SSLCommerz, bKash, etc.) requires merchant accounts, SSL certificates, and compliance paperwork — impractical for a demo/personal project. Yet the app still needed a realistic booking flow that confirms payment before issuing tickets.


How I solved it: Designed a manual payment verification workflow. Users submit a transaction ID and a screenshot reference during booking. The booking is created with paymentVerified: false. Admin has a dedicated "Verify Booking" screen that lists all unverified bookings, shows the submitted transaction ID, and toggles paymentVerified to true with a single button tap. The user receives a Firebase Cloud Messaging notification when verification completes, and the ticket becomes downloadable as a QR code only after verification.

Cross-Platform Navigation with Expo Router

The app features a complex navigation tree: authentication screens (login/signup), a bottom-tab layout (Home, Bookings, Profile, Admin), and modal screens for bus selection, seat layout, payment, and ticket details. Managing deep navigation links and preventing back-navigation to auth screens after login required a structured routing approach.


How I solved it: Adopted Expo Router with file-based routing for a clean, declarative navigation structure. Auth screens live in app/(auth)/ and are gated by a root _layout.tsx that checks useAuth() — redirecting to (tabs) if authenticated. The tab layout nests four tabs, and modal screens like app/bus/[id].tsx use Stack screens with presentation: "modal". This approach eliminated manual navigation state and made the route tree self-documenting.

Dynamic Seat Grid UI with Availability States

The seat selection screen needed a visual grid where each seat has four states — available, selected, locked-by-other, and booked — each with distinct colors and interaction rules. The grid must display seats in a 4-column layout and enforce that the number of seats is divisible by 4 for proper alignment.


How I solved it: Built a SeatGrid component that takes totalSeats, bookedSeats[], lockedSeats[], and selectedSeats[] as props. Each seat is rendered as a touchable that checks its state against all three arrays using .includes(). CSS classes map states to colors: green for available, blue for selected, gray for locked, red for booked. The component validates that totalSeats % 4 === 0 at render time, and the bus seeding data ensures this constraint is always met.

Smart Bus Search with Date-Aware Sorting

Users search for buses by origin, destination, and date. Buses departing today should show remaining seats in real-time, while future buses need different sorting (by departure time). Performing this with Firestore's limited query capabilities — no native JOINs or full-text search — required careful index design.


How I solved it: Created composite Firestore indexes on buses for origin + destination + date. The search function runs two parallel queries — one for today's buses (filtering by date == today and sorting by departureTime) and one for future dates (filtering by date >= tomorrow and sorting by date). Results are merged client-side with today's buses displayed first. Each bus card shows real-time seat availability as totalSeats - bookedSeats.length - lockedSeats.length.
