Task Poster App

2025App React Native · TypeScript · Expo · Firebase
GitHub Live

A React Native mobile app built with Expo and Firebase for posting and managing tasks — real-time sync, cross-platform support, and a clean task workflow.

Problem

Teams and individuals needed a simple mobile tool to post, assign, and track tasks without the overhead of heavyweight project management tools.

Solution

Designed a lightweight task management mobile app using React Native and Firebase, enabling users to create, update, and track tasks with real-time sync across devices.

Key Features

  • Task creation and assignment
  • Real-time sync with Firebase
  • Cross-platform (Expo)
  • Task status tracking
  • Clean, minimal interface

Challenges & Engineering Deep Dive

Distributed Data Consistency Across Collections

The app spans five Firestore collections — users, worked, complains, notifications, and admins. A single action like "accept a task" must update the user's acceptedWorks array, flip the worked document status to "accepted", write a notification, and conditionally pull the poster's contact info.


How I solved it: Designed atomic Promise.all chains for multi-document updates and used Firestore's built-in arrayUnion / arrayRemove helpers to avoid race conditions. Each write is wrapped in try/catch with user-facing Alert.alert fallbacks so partial failures never leave the UI in an inconsistent state.

Weighted Rating System Without a Backend

Tasks required a fair, tamper-resistant rating system. The naive average — summing all ratings and dividing by count — would let a single new rating swing the score unfairly. I needed a weighted running average that stayed accurate even with hundreds of ratings, all computed client-side in Firestore.


How I solved it: Implemented the classic weighted average formula: newRating = (oldRating × oldRatingCount + newRating) / (oldRatingCount + 1). Each rating submission is an idempotent transaction — the reviews array uses arrayUnion to prevent duplicates, and the status field is flipped to "completed" atomically in the same updateDoc call. This guarantees exactly one rating per completed work, no matter how many times the button is pressed.

Task Lifecycle State Machine

A task moves through a strict state machine: pending → accepted → completed. Each transition triggers cascading side effects — contact info disclosure, notification creation, wallet implications, and UI re-renders across multiple screens.


How I solved it: Encoded the state machine directly in Firestore queries. Screens like pendingwork.tsx filter WHERE status == "accepted" while completedwork.tsx filters WHERE status == "completed". The "Complete" button is gated behind a secondary acceptedBy check so only the assigned user can transition the state. This keeps the logic declarative and eliminates hidden state bugs.

Real-Time Feed Without Over-fetching

The home screen uses Firestore onSnapshot to show new tasks instantly. Without careful management, every keystroke or navigation event could trigger a new listener — draining the user's data plan and hitting Firestore read quotas.


How I solved it: Attached a single onSnapshot query in a useEffect with an empty dependency array so the listener is registered exactly once per mount. The cleanup function (unsubscribe) is called on unmount, preventing zombie listeners. For the category-filtered view, I combined where("category", "==", selectedCategory) with compound queries to minimise document scans.

Cross-Platform Polish Without Fragmentation

Android and iOS handle status bars, safe areas, and shadows completely differently. A hardcoded padding that looks perfect on iOS can overlap the status bar on Android, and elevation (Android) has no effect on iOS where shadowOffset is required instead.


How I solved it: Added Platform.OS checks in every screen's header style. For Android: paddingTop: StatusBar.currentHeight || 0. For iOS: a static paddingTop: 20 (standard safe-area inset). Shadow effects use both elevation (Android) and shadowColor / shadowOffset / shadowOpacity / shadowRadius (iOS) in the same style block, so the visual result is identical on both platforms.

Admin Aggregation Without SQL

Firestore doesn't support GROUP BY or COUNT(*) — yet the admin dashboard needs real-time stats: total users, active posts, pending jobs, completed jobs, and complaint volume. Running 5+ separate getDocs queries on every visit is slow and expensive.


How I solved it: Batched all aggregation queries inside a single fetchStats async function using Promise.all for parallel execution. Each stat runs a targeted where filter (e.g., where("status", "==", "active")) so Firestore only scans matching documents. The loading state is managed with a single useState toggle, and errors are caught globally so a single failed query doesn't crash the entire dashboard.

Contact Privacy by Design

Phone numbers and contact details are sensitive — they shouldn't be visible to everyone browsing the task feed. But once a user accepts a task, they need a way to reach the poster. The challenge was balancing transparency with privacy without a proper backend or role-based API gateway.


How I solved it: Contact info is never displayed in the task feed or user list. It's only revealed through an Alert.alert triggered by a "Contact" button that appears after a task has been accepted. The phone number is fetched via a direct getDoc lookup on the poster's user document — so it's gated behind both authentication and an accepted-work relationship, not just client-side UI hiding.

Complaints & Resolution Workflow

Building a complete complaint system — user submits → admin reviews → admin sends feedback → status marked "solved" — introduced coupling between screens and required relational lookups (fetching user names by fromUserId for each complaint). Error handling had to span three separate screens.


How I solved it: Used a for... loop with individual getDoc calls to resolve fromUserId to fullName when fetching complaints (the collection is small so N+1 is acceptable). The status toggle ("pending" → "solved") is handled by updateDoc inside the feedback submission handler. Complaints are sorted client-side with sort() so admins see pending issues first.
